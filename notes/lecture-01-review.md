日期：2026-10-21。依据本讲 slides 复盘，课程规则为讲义中记载的要求；具体作业说明与 Canvas 为正式要求及截止时间的权威来源。

## 我的首轮回答

1. 最小 agent 循环：上下文 + 历史 + 工具 + 问题 → 模型。模型负责规划、推理；框架负责管理上下文、工具、历史。保留上一步结果、工具调用、日志；任务完成时结束。
2. 六项能力：准确工具调用、长上下文统一、可自定义、复杂任务管理、环境理解、安全性。重复调用和不调用属于失败；长程任务无法保持连贯或超过上下文限制会影响理解。
3. 沙箱防范代码越权修改文件，凭证限制保障个人信息和外部攻击，轨迹监控防止模型不受控。沙箱与正式环境可能不一致；其余两项局限不清楚。
4. Harness 管工具、上下文、历史；Sandbox 运行代码；Inference 生成回答；Training systems 优化 agent；Monitoring 监控。工具权限校验、KV cache 复用由 Harness 负责，故障轨迹记录由 Monitoring 负责。
5. 对 A1、A2、A3 的成果和可靠评估不太了解。
6. 对课程要求不太清楚。

## 统一反馈与补充

### 1. 行动循环：基本正确

模型还负责选择行动、生成工具调用或最终回复；框架解析、校验、执行并将结果写入历史。每轮使用更新后的历史调用模型。摘要或历史应保留目标、约束、关键行动和观察，不能仅依赖上一步结果。除完成外，还应有步数、时间或成本预算等退出条件；超限退出要如实报告未完成。

### 2. 能力：六项列举正确，方法尚未作答

重复调用与不调用不必然是失败：暂时性错误重试、修改后重新测试可以合理；已有充分信息时可以直接回答。应判断是否有必要、是否产生新证据以及是否推进任务。

| 能力 | 模型训练路径 | 框架工程路径 |
| --- | --- | --- |
| 准确工具调用 | 工具调用轨迹 SFT | 语法约束解码、参数验证；格式验证不保证语义正确 |
| 长上下文连贯性 | 长上下文 SFT | 压缩摘要、动态检索、合适的子任务委派 |

### 3. 安全：方向部分正确，需要区分限制、检测与阻断

- 沙箱限制文件、网络、计算资源和执行范围。指出与正式环境可能不一致是合理局限；允许范围内仍可能出现错误操作和错误结果。
- 凭证访问限制降低读取秘密或访问敏感服务的能力。它不能阻止已有权限被错误使用，也不能单独防范所有外部攻击。
- 轨迹监控记录并帮助发现异常、失败和成本。单纯记录不会自动停止行为，需与告警、权限检查或终止机制结合；已发生的损害也不会因为有日志而自动撤销。

上述局限是对讲义所列安全方法的工程解释。

### 4. 工程分工：KV cache 归属需要纠正

| 组件 | 职责 |
| --- | --- |
| Harness | 状态、工具、上下文、记忆、控制流程、动作校验及错误处理 |
| Sandbox | 隔离执行并限制文件、网络与计算资源 |
| Inference | 模型生成、请求批处理、流式输出、KV cache 复用与吞吐管理 |
| Training systems | 数据与 rollouts、分布式训练、检查点与训练评估 |
| Monitoring | 轨迹、质量、时延、成本与失败记录 |

工具权限校验 → Harness；KV cache 复用 → Inference；故障轨迹记录 → Monitoring。此前将 KV cache 复用分给 Harness 是本题的明确错误。

### 5. 作业与可靠性证据：本轮补充

依据第 33 页概览：A1 构建基础框架并建立可复现基线；A2 测量行为、报告失败案例，区分演示与证据；A3 训练或适配组件，并分析行为、成本与鲁棒性。具体提交物依各作业说明。

可检查的成果示例：A1 是可运行的控制器与可复现运行记录；A2 是任务集、指标、结果和失败分析；A3 是可复现的训练或适配设置，以及相对基线的效果、成本和鲁棒性比较。

单个成功演示不能说明整体可靠。应明确任务分布与成功标准，在多个任务上测量成功率、调用或 token 成本、时延、失败类型及必要的重复运行稳定性，并保存可复现配置和轨迹。

### 6. 课程要求：依据第 35–38 页补充

- 先修要求：具备实质性的语言模型训练经验；正式选课是否满足要求由课程方审核。
- A1–A3 个人完成，共占 40%；个人 Lecture highlights 占 10%；2–3 人研究项目占 50%。项目 proposal 5%、check-in 5%、presentation 10%、final report 30%。
- 课程通常允许 AI 工具，但具体作业或项目说明可另有限制；Lecture highlights 必须本人撰写，不能由 AI 生成。提交者对主张、引用、结果和代码负责。
- 正式要求与截止时间以作业说明和 Canvas 为准，概览中的暂定日期不作为最终依据。
- 讲义还记载：A1–A3 每项有两个 24 小时 slack days，不能转移；用完后每额外一天或不足一天扣该作业分数的 5%。项目 proposal 与 report 各有两天，presentation 没有。

## 集中补答

1. 同一测试工具在修改代码后再次调用，为什么可能合理？什么情况属于无效重复？
2. 只记录完整轨迹，能否阻止一次越权删除？应由哪些机制负责限制或阻断？
3. 要证明新 Agent 比基线可靠，你会如何安排评估任务、指标与对照？

## 集中补答与反馈

我的补答要点：

1. 调用失败、需要继续浏览网页等情况可以再次调用；任务不推进、多次失败属于无效调用的可能表现。
2. 完整轨迹不能阻止越权删除，还需联动权限检查或终止机制。
3. 评估任务成功率、完成次数、完成时间、工具调用次数和 token 数。

统一反馈：三题核心方向正确。第一题还需按错误类型判断是否适合重试；多次失败并非单独的判据，应检查是否有新信息、条件变化和继续尝试的理由。第二题正确。第三题提供了有用的指标，但对照设计尚需补充：同一任务集、明确成功标准、匹配预算，并在有随机性时重复运行；成功次数应连同任务总数报告。成本指标需要与成功率一起比较。
