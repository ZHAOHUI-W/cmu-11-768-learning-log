## 开场讨论：能力与行动边界

讲义开场展示复杂任务的执行能力，并讨论不同任务应允许怎样的自主行动。评价智能体需要考虑任务完成能力、结果的可靠性、授权范围和行动后果。

理解练习：用户要求修复网站结账失败，智能体修改代码后本地测试全部通过。部署前还需要确认什么？

我的初始回答：“检查失败原因，修复方法。”

补充反馈：这两项有助于判断修复是否针对根因；上线还需要确认部署授权，以及线上环境、测试覆盖和回滚条件。本地测试通过并不能单独决定是否可部署。

## 基础定义：观察与环境状态

智能体通过观察获得环境信息，再采取行动影响环境。观察可以是日志、文件、截图和工具输出；环境状态包含系统的真实情况，其中有些信息尚未被观察到。同一条观察可能对应多种状态。

理解练习：日志显示“支付请求超时”，是否足以确定失败原因？

我的回答：“可能是支付请求接收方未在时间内反馈，或者支付请求本身发送失败。”

反馈：回答识别出同一观察可能有不同原因。第二种可以进一步区分连接或发送阶段超时，与立即返回错误的发送失败。仅凭“超时”还不能确定失败发生在哪个阶段，需要进一步观察。

## 语言模型回顾：推理与外部证据

理解练习：只有“支付请求超时”这一日志，诊断智能体不调用工具，仅生成更多推理 token，能否确认具体原因？

我的初始回答：“没有调用工具，那就是说明支付请求未发送。”

纠正反馈：题目中的工具调用属于诊断智能体；支付请求属于网站原先执行的业务流程。诊断智能体本轮未调用工具，并不能说明网站此前未发送请求。请求已到达但响应延迟，以及连接或发送阶段超时，都可能产生相同日志。

更多推理可以整理现有信息和提出假设，但不能单独提供新的外部观察。这个区别仍需通过下一道检查题巩固：需要取得什么外部记录，才能判断请求是否到达接收方？

## 外部证据：接收方记录

对于“判断请求是否到达接收方应读取什么记录”，我的回答是“接收方的对应 HTTP 协议中的 JSON”。

反馈：取证方向是接收方。如果 JSON 是接收方已经记录的请求，可以提供证据；发送方准备好的 JSON 不能证明请求到达。JSON 是数据格式，关键是记录来自哪里，以及是否包含对应 request_id、接收事件和时间戳。没有找到日志也不等于请求一定没有到达，还需考虑日志覆盖与查询范围。

这个需求可以转成明确的工具定义：工具名称、用途说明，以及必填的字符串参数 request_id。

## 工具定义：明确参数

理解练习：为什么必填的 request_id 比“帮我查一下支付问题”更适合执行？

我的回答：“不需要模型再判断意图，减小工具调用出错的概率。”

反馈：回答指出了减少歧义和错误的作用。更准确地说，模型仍需要判断用户意图、选择工具并填入正确的 ID；框架可以依据明确的参数查询，并检查缺失或类型错误。参数结构正确，也不保证 ID 在语义上正确。

## 工具调用与结果的对应关系

业务 request_id 标识支付请求；工具调用 ID 标识智能体发起的一次具体查询，返回消息通过 tool_call_id 与该调用关联。

理解练习：同一个 pay_123 先后被查询两次，两次调用 ID 是否应该相同？

我的回答：“不同，工具调用 ID 应该具有时间上的唯一性。”

反馈：两次新调用应能分别识别。更准确地说，ID 的作用是在相关交互范围内唯一关联调用和结果；不必包含时间戳，也不能仅靠 ID 推断执行顺序。

讲义第 13–14 页的行动循环：模型生成调用 token，框架解析、验证并执行，环境结果作为观察进入上下文，再供下一轮模型预测。

## 将工具结果写入历史

理解练习：执行工具后、再次调用模型前，应向 messages 加入什么？

我的初始回答：`messages.append(result.tool_call_id)`。

纠正反馈：只添加调用 ID 缺少工具输出，模型无法据此获得执行结果。应加入完整的工具结果消息；role 表示消息来自工具，tool_call_id 对应原调用，content 保存实际观察。调用 ID 应从原调用取得，工具返回值未必带有这个字段。

以下为单次工具调用的概念伪代码，假设 result 是工具返回的文本：

```python
messages.append({
    "role": "tool",
    "tool_call_id": reply.tool_call.id,
    "content": result,
})
```
